# openWakeWord Windows Training Pipeline

A **Windows-only**, local, reusable pipeline for training custom [openWakeWord](https://github.com/dscripka/openWakeWord) models, without needing WSL/Linux for the synthetic sample generation step. Built while training a custom wake word for a Home Assistant voice satellite; generalized here as a template so a new wake word is just a config swap away. Setup and orchestration are PowerShell (bundled with every Windows install — including auto-installing Git and Python themselves via `winget` if you don't already have them); the actual ML training work underneath is Python, same as any openWakeWord pipeline.

This is **code + patches + config**, not a full standalone package: you clone openWakeWord yourself, apply the small patch here, drop these scripts in, and follow the steps below. Large binaries (trained models, voice packs, feature caches, audio clips) are intentionally not included — they're either downloaded once (see below) or generated by running the pipeline.

## Why this exists

openWakeWord's own official training notebook is fast and well-documented, but Linux-only — it depends on `piper-sample-generator`, which historically required the Linux-only `piper-phonemize` package. This pipeline swaps that one function (`generate_samples()`) for a native-Windows implementation (`scripts/generate_samples_piper.py`) built on the official `piper-tts` PyPI package, which does ship a prebuilt Windows wheel. Everything downstream (augmentation, feature extraction, training) is plain PyTorch/NumPy and doesn't care how the WAV files were made.

**If you'd rather just use the real, current `piper-sample-generator`:** as of its v3.2.0 "move to package" refactor, it no longer depends on `piper-phonemize` at all — it uses the same `piper-tts` native API this repo does. It still won't build on native Windows today only because one of its dependencies (`webrtcvad`) ships no prebuilt wheels for any platform and needs a C compiler. The cleanest path there is WSL2 + Ubuntu (`wsl --install -d Ubuntu`), which has real compilers and manylinux wheels for everything. Either path works; this repo documents the native-Windows one since it avoids needing WSL at all.

## Quick install

**No prerequisites needed** — not even Python. Everything below is PowerShell (bundled with every copy of Windows), and it installs Git and Python itself via `winget` if either is missing.

```bash
git clone https://github.com/DisasterofPuppets/Open-Wake-Word-Training.git
cd Open-Wake-Word-Training
```
(or just download the repo as a ZIP from GitHub and extract it, if you don't have git yet either)

**Recommended: double-click `installer_gui.bat`.** One window, three tabs (Install / Download Assets / Train), a GPU-vs-CPU picker at the top, real progress bars and live logs. A PowerShell console stays open behind it — that's normal, it shows output from prerequisite checks (installing git/Python via winget, if needed).

**Or three separate double-click scripts, run in order, if you prefer plain console output:**

| | Script | What it does |
|---|---|---|
| 1 | **`install.bat`** | Installs git/Python if missing, sets up the venv, installs Python packages + torch (GPU or CPU, asks or auto-detects), clones openWakeWord + applies the Windows patch. No large downloads. |
| 2 | **`download_assets.bat`** | Downloads the voice pack / RIRs / feature cache. Shows the total size (**~16.5GB**) upfront and asks to confirm before downloading anything. |
| 3 | **`Train.bat`** | Menu: standard training (prompts for wake phrase, runs generate → train → convert → verify → package) or bulk training with real recordings mixed in. |

`install.bat` also works as a **standalone bootstrapper** — if you download just `install.bat` + `install.ps1` together (before cloning anything) and double-click `install.bat`, it'll clone the repo into a fresh `OpenWakeWordTrainer` folder next to itself and run setup there.

Every script here is safe to re-run — each step skips anything already done. The rest of this section documents what gets automated, for anyone who'd rather do it by hand or is troubleshooting a failed step.

## One-time setup (manual reference)

These steps only need doing once; everything downloaded here is reused across every future wake word.

### 1. Clone openWakeWord and apply the Windows patch

```bash
git clone https://github.com/dscripka/openWakeWord
cd openWakeWord
git apply /path/to/this/repo/patches/openwakeword-windows-fixes.patch
pip install -e .
```

The patch fixes three Windows-specific issues (all root-caused the hard way — see "Why these patches exist" below):
- `train.py`: swaps the `generate_samples` import to this repo's native-Windows version; forces `num_workers=0` on the training DataLoader (Windows' `spawn`-based multiprocessing can't pickle the lambda closures used elsewhere in the pipeline)
- `data.py` / `utils.py`: explicitly releases numpy memory-mapped file handles (`del` + `gc.collect()`) before delete/rename operations — Windows, unlike POSIX, refuses to delete or rename a file that's still memory-mapped open

### 2. Set up the venv

```bash
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

REM torch/torchaudio are installed separately -- CPU:
.venv\Scripts\pip install torch==2.9.1 torchaudio==2.9.1
REM ...or GPU (CUDA build this pipeline was verified against):
.venv\Scripts\pip install torch==2.9.1 torchaudio==2.9.1 --index-url https://download.pytorch.org/whl/cu128
```

Then copy `patches/sitecustomize.py` into `.venv\Lib\site-packages\sitecustomize.py`. This file is auto-imported by Python on every startup and applies two more Windows fixes:
- Aliases `scipy.special.sph_harm` → `sph_harm_y` (the `acoustics` package, used for one noise-generation helper, imports the old removed name)
- Replaces `torchaudio.load()` with a plain `soundfile`-based implementation (current `torchaudio` routes through `torchcodec`, whose native DLL doesn't reliably load on Windows; openWakeWord only uses `torchaudio.load()` to read WAV files, so this is a safe drop-in)

### 2b. openWakeWord's own feature/VAD models

`install.py` also downloads three small required models (melspectrogram, embedding, silero_vad) straight from `openwakeword.utils.download_models()` right after cloning/patching openWakeWord -- separate from the three big shared-asset groups below, and not something `download_assets.py` touches. This happens automatically; nothing to do here.

### 3. Download the shared training assets

`download_assets.bat` (or `scripts/download_assets.py`) does this whole step for you — prints the size of each asset group and a grand total (~16.5GB) before asking to confirm, then downloads all three groups below, skipping anything already present. **No Hugging Face account or API key is needed** — all three sources are public repos; an optional free token (used only for that run, never saved) just makes the big feature-cache file faster.

**Already have any of these from a previous project or another machine?** The script asks, for each asset group, whether you already have it somewhere and takes a path instead of downloading — it copies (or moves, your choice, for the big feature-cache file) whatever it finds, validating file size for the two big feature files first. Manual instructions follow, for reference:

- **Stock multi-speaker Piper voices** (for synthetic sample generation) — download into `stock_multispeaker_voices/`:

  | Voice | Speakers |
  |---|---|
  | `en_US-libritts_r-medium` | 904 |
  | `en_US-libritts-high` | 904 |
  | `en_GB-vctk-medium` | 109 |
  | `en_US-l2arctic-medium` | ~24 |
  | `en_US-arctic-medium` | ~18 |

  Each is a `.onnx` + `.onnx.json` pair from the [Piper voices repo on Hugging Face](https://huggingface.co/rhasspy/piper-voices).

- **Room impulse responses** (reverb augmentation) — any WAV-format RIR set works; the [MIT IR Survey](https://mcdermottlab.mit.edu/Reverb/IR_Survey.html) is a good free option. Put the WAVs in `augmentation_data/room_impulse_responses/`.

- **ACAV100M precomputed negative features** — openWakeWord's standard large negative-audio feature set. Follow the download link in [openWakeWord's own training docs](https://github.com/dscripka/openWakeWord/tree/main/notebooks). This is a large (~17GB) file — if downloading from Hugging Face:
  - **Get a free HF access token first** (huggingface.co/settings/tokens, "read" scope) and pass it as `Authorization: Bearer <token>` — unauthenticated requests to large dataset repos can be throttled to ~20KB/s, vs several MB/s authenticated.
  - **Use `aria2c` with multiple connections** (`aria2c -x16 -s16 -k10M ...`), not a single-connection tool — single-connection downloads of this specific file were observed to throttle back down mid-transfer even when authenticated, regardless of tool.

Put the config's `feature_data_files` and `false_positive_validation_data_path` paths pointing at wherever you save these.

## Per-wake-word quick start

Once step 1 (install) and step 2 (download assets) have both been run:

**Using the GUI (`installer_gui.bat`):** the "3. Train Wake Word" tab has fields for the wake phrase, model name, display name, sample count, cutoff, and an "Add..." button to pick real WAV recordings to test against — fill them in and click Train.

**Or double-click `Train.bat`:** pick standard or real-samples mode, then it prompts for the same things at the console and runs everything below — config generation, synthetic sample generation, augmentation, training, TFLite conversion (with the critical anti-transpose flag), shape verification, and packaging the final `.tflite` + `.json` — end to end.

**Or from a terminal**, same script either way, args optional (omit any and it'll prompt):
```bash
.venv\Scripts\python.exe scripts\train_wake_word.py --phrase "hey computer" --name hey_computer
```
Run `--help` for the full flag list.

Either way, this is a good point to skip ahead to "Deploy to Home Assistant" below once it finishes. The rest of this section explains what happens under the hood, step by step, for troubleshooting or if you'd rather run it by hand.

### What happens under the hood

1. **Config**: copies `config/wake_word.example.yaml`, filling in `model_name` and `target_phrase`. Every other path in the config is plain-relative to wherever `train.py` is run from (its own CWD, not the config file's location) -- there's no path-substitution placeholder; don't hand-type `<PROJECT_ROOT>` or similar into a config, it won't be resolved.
2. **Generate + augment + train**, all via openWakeWord's own `train.py`:
   ```bash
   set PYTHONUTF8=1
   python openWakeWord/openwakeword/train.py --training_config config/my_new_word.yaml --generate_clips --augment_clips --train_model
   ```
   (`PYTHONUTF8=1` avoids a `UnicodeEncodeError` from a checkmark character `torch.onnx`'s exporter prints, which crashes on the default Windows console codepage.) This produces `<output_dir>/my_new_word.onnx`. **Ignore** any crash immediately after that from a broken `onnx_tf` import — the script unconditionally attempts its own (long-abandoned, broken) ONNX→TFLite conversion after training regardless of whether you asked for it; the ONNX file you need is already written by that point.
3. **Convert to TFLite — the critical step:**
   ```bash
   REM a separate venv (.venv-convert), to avoid onnx/protobuf version conflicts with the training venv.
   REM onnx2tf itself declares ZERO hard pip dependencies by design (so it never forces a
   REM tensorflow/onnx version on you) -- every one of these has to be listed explicitly, or
   REM you get a ModuleNotFoundError deep inside onnx2tf the first time that code path runs.
   pip install onnx2tf onnx onnx-graphsurgeon sng4onnx psutil tensorflow tf_keras ai-edge-litert
   python -m onnx2tf -i my_new_word.onnx -o tflite_output -kat x
   ```
   Pin `onnx` to whatever version is already proven working in your *main* training venv
   (check with `pip show onnx` there) -- it already shares the same protobuf your `tensorflow`
   install needs, so that's a known-good pairing rather than a guess.
   **The `-kat x` flag is not optional.** Without it, `onnx2tf` applies a default NCHW→NHWC-style axis-reordering heuristic that misidentifies this model's plain `(1, 16, 96)` feature tensor as needing transposition, silently producing a `(1, 96, 16)` model that is structurally incapable of correct inference — it will train fine, pass synthetic validation, and then simply never fire on real speech, with no error anywhere in the chain. This exact bug cost an entire debugging cycle before being found (see "Why these patches exist" below).
4. **Verify the shape** before trusting anything:
   ```python
   import ai_edge_litert.interpreter as tflite
   interp = tflite.Interpreter(model_path="tflite_output/my_new_word_float32.tflite")
   interp.allocate_tensors()
   shape = interp.get_input_details()[0]["shape"]
   print(tuple(int(v) for v in shape))  # MUST print (1, 16, 96)
   ```
   Cast each value to a plain Python `int` before printing/comparing. NumPy 2.x changed how a
   `numpy.int32` reprs *inside a tuple* (`np.int32(1)` instead of bare `1`) -- a naive
   string-compare against `"(1, 16, 96)"` will report a false mismatch on a perfectly correct
   model if you skip the cast.
5. **Package**: copies the verified `.tflite` and writes the `.json` sidecar into `model_output/`.
6. **Verify against real speech before deploying** — record yourself (and ideally someone else) saying the wake phrase a few times into a WAV file, then:
   ```bash
   python scripts/eval_real_voice.py model_output/my_new_word.tflite my_recording.wav
   ```
   This runs the actual TFLite interpreter (not `openwakeword.Model()`'s Python wrapper, which **silently falls back to a sibling `.onnx` file on Windows** if `tflite-runtime`/`ai_edge_litert` isn't importable — a false-positive test that will tell you your `.tflite` "works" when it was never actually loaded) through the same 80ms streaming chunks the production runtime uses, and reports per-chunk detection scores. Confirm it fires (score ≥ your cutoff) on real speech, not just synthetic validation data, before shipping it.

### Deploy to Home Assistant

Build a sidecar JSON next to the `.tflite`:

```json
{
  "type": "openWakeWord",
  "wake_word": "My New Word",
  "model": "my_new_word.tflite",
  "trained_languages": ["en"],
  "openWakeWord": { "probability_cutoff": 0.7 }
}
```

Copy **both files** to:
1. The openWakeWord add-on's model directory (typically `\\<homeassistant-host>\share\openwakeword\`) — required for the wake word to be selectable in the openWakeWord integration.
2. Each Assist Satellite's own local wake-word folder (e.g. `\\<homeassistant-host>\share\assist_satellite\local\external_wake_words\` for a `linux_voice_assistant`-based satellite) — a satellite only *lists* wake words present in its own local folder, separately from the central add-on.

Then set it as the **active** wake word via Settings → Devices & Services → the satellite's integration (e.g. ESPHome) → the device → wake word selection. A satellite's local YAML config field for wake word does not control the active selection by itself.

## Notes on the GUI (`installer_gui.ps1`)

- A PowerShell console window stays open behind the GUI — that's expected, not a bug. It's the same process hosting the GUI, and prerequisite-check output (git/Python install via `winget`) prints there rather than in a tab's log box.
- Each tab's progress bar is driven by parsing that step's own text output for `(NN%)` markers (present during downloads) or `=== section ===` headers; steps with neither just show an indeterminate animation. It's a real progress indicator, not a simulated one, but its granularity depends on what the underlying script prints.
- The three tabs are independent background jobs — you can switch tabs while one is running. Steps 2 and 3 need step 1 (the venv) to exist first; if you jump ahead, the job's log will say so plainly rather than silently failing.

## Why these patches exist (condensed troubleshooting log)

- **`num_workers=0` on Windows**: the training DataLoader defaults to multiprocess workers via `spawn` on Windows (vs `fork` on Linux/Mac), which requires pickling everything passed to workers — including lambda closures the pipeline uses elsewhere, which Windows can't pickle. Single-process loading has no meaningful cost here since the data already comes from memory-mapped arrays.
- **Memmap `del` + `gc.collect()` before delete/rename**: numpy memory-mapped files opened for writing are never explicitly closed before the code tries to `os.remove()`/`os.rename()` them. POSIX allows deleting/renaming an open-mapped file; Windows raises `PermissionError`. Every memmap along the code path needs releasing — `del` alone is not reliably sufficient, `gc.collect()` is also needed to actually drop the last reference.
- **`onnx_tf` is a dead end**: unmaintained since ~2022, needs a removed `onnx.mapping` API, and depends on `tensorflow_addons` (archived by Google). Use `onnx2tf` instead (actively maintained) — **with `-kat` on the input tensor name**, or you'll hit the transpose bug described above.
- **`onnx2tf` declares zero hard pip dependencies, on purpose** (so it never forces a tensorflow/onnx version on you) -- every package it imports anywhere in its source (`onnx`, `onnx_graphsurgeon`, `sng4onnx`, `psutil`, plus `tensorflow`/`tf_keras`/`ai-edge-litert`) has to be installed explicitly, or you get a `ModuleNotFoundError` deep inside it the first time that specific code path runs -- which can be months after the venv was first set up, since most of its branches are never hit by a plain `-i ... -o ... -kat x` conversion.
- **Pin the convert venv's `onnx` version to what's already proven in the main venv**, not to an unrelated reference/freeze file -- the convert venv already shares the same `protobuf` version your `tensorflow` install pulled in, and an `onnx` version that hasn't been checked against that specific `protobuf` is a guess, not a known-good pairing.
- **openWakeWord's own `install_requires` only ships a minimal base** -- torchinfo, torchmetrics, PyYAML, audiomentations, torch-audiomentations, speechbrain, mutagen, and (for uncommon target phrases containing a word outside CMUdict) deep-phonemizer are all only in its optional `full` extras group. `install.py` deliberately runs a bare `pip install -e .` (no extras) to avoid also pulling in tensorflow/datasets/onnx_tf, so every one of those had to be hand-curated into `requirements.txt` here instead -- `torch.onnx.export()`'s own newer exporter path additionally needs `onnxscript`, which isn't declared by openWakeWord at all.
- **`acoustics` package import chain crashes** on `scipy.special.sph_harm` (removed in current scipy in favor of `sph_harm_y`) even though the actual function used (`acoustics.generator.noise()`) never touches the broken code path — the alias in `sitecustomize.py` fixes the import without needing an older scipy.
- **`torchaudio.load()` always routes through `torchcodec`** in current torchaudio versions (the old soundfile/sox_io backend was removed); if `torchcodec`'s native DLL doesn't load on your machine, replace `torchaudio.load` with a plain `soundfile`-based function matching the same return signature — see `patches/sitecustomize.py`.
- **A partial/crashed feature-computation run can leave a stale cache file behind** that fools the "already computed, skipping" resume check (which only checks for the existence of one of several output files) — if a stage was interrupted, check whether *all* expected output files exist before trusting a "skipping" message, or just pass `--overwrite`.
- **The real root-cause bug**, found only by testing against real recorded speech instead of trusting synthetic validation metrics: the ONNX→TFLite conversion step can silently transpose the model's input tensor axes (see above). A model with this bug trains cleanly, exports without error, and passes every synthetic validation check — the only way to catch it is checking the actual `.tflite` file's input shape, or (more robustly) running real audio through it end-to-end before deploying.
- **`torch`/`torchaudio` are installed separately from `requirements.txt`**, not pinned in it: a plain `pip install -r requirements.txt` would silently grab PyPI's default (CPU-only) Windows wheel even on a GPU machine, since CUDA wheels only exist on PyTorch's own package index. `install.py --gpu`/`--cpu` (auto-detected from `nvidia-smi` if neither is passed) installs the right one explicitly with `--index-url` when GPU is requested.
- **Winget-installed tools (git, Python) aren't on `PATH` in the current process** until the shell restarts — `install.ps1` re-reads `PATH` from the registry (`Update-SessionPath` in `scripts/InstallerCommon.ps1`) immediately after installing either, so the rest of setup can use them without needing a fresh terminal.
